# PRODUCT_PLAN（Phase1 专用；Readiness 定义唯一正典，卡内引用不重写）

- Plan Version：PRODUCT_PLAN_V0.2（闭环首轮 Research Review Required Fixes 与 2026-09-18 12:55 人类决策回执）
- PROJECT_PHASE：PLAN
- Product Goal：把首页实时雷达升级为可配置的多标的观察盘。候选币池以 OKX 公开且应用可拉取的永续合约范围为准；用户用名称/代码搜索与收藏选择标的，在 4/6/9 三档布局间切换，并保证一币一卡、不重复。每张卡继续展示可解释的状态、证据来源、时间戳与 freshness；产品不输出面向交易决策的胜率、收益承诺或开仓建议。
- Target Users：需要在单用户本地部署中同时观察多个加密资产 4H 突破状态、重视证据链与数据新鲜度、但不希望被概率化收益话术或交易指令误导的现有雷达用户。
- Problem：
  - 当前首页固定渲染 PEPE、DOGE、ETHFI 三张信号卡，用户不能改变观察数量、收藏标的或切换单卡标的。
  - 当前标的类型、行情汇总响应、数据新鲜度区块及部分页面逻辑仍有三币硬编码，不能承载受控扩展的 OKX 永续候选池。
  - 原冻结范围仅 PEPE、DOGE、ETHFI，BTC 为环境参照；扩大实时观察范围属于产品与架构边界变更，现已由人类决策确认按 CHANGE C 处理。
  - 新标的缺少独立历史研究基线，不能借用 PEPE/DOGE 的研究统计，也不能把统一观察规则描述为已验证有效。
- Core Value：用户可在一个稳定观察盘内保存收藏与布局并快速切换标的；每张卡仍明确展示当前状态及证据质量。扩展的是实时观察范围，不是对新标的有效性、收益或交易机会作承诺。
- User Flow：
  1. 用户进入首页，服务端从本项目独立 SQLite 数据库读取当前单用户配置；无有效配置时使用 4 卡默认布局。
  2. 用户在 4/6/9 中选择档位；档位即布局，分别呈现 4、6、9 个卡槽，币数与槽位一一对应。
  3. 用户打开标的选择器，按名称或代码搜索 OKX 永续候选币，并可添加或取消收藏。
  4. 用户为某个卡槽选择一个已启用标的；已被其他卡占用的标的不可再次选择，始终保持一币一卡。
  5. 档位增大时，按“收藏优先、注册表稳定顺序次之”补入尚未占用且已启用的标的；不足时显示明确空槽。档位减小时保留前 N 个卡槽，被移除卡槽的标的不再显示但收藏不变。
  6. 布局或收藏变更通过应用 HTTP API 写入服务端 SQLite；刷新或重启本地服务后恢复。配置损坏、标的停用或 schema 不兼容时安全迁移，无法迁移则回退默认配置并给出原因。
  7. 卡片仅展示所选标的的实时信号、价格、证据、来源时间与 freshness；数据缺失、过期或不可用必须显式显示，不以 0 或历史快照冒充实时值。
  8. 用户进入详情、历史、相似性或方法论时，无独立研究基线的标的显示“未知/缺失”或不展示相关指标，不借用其他标的统计生成概率化结论。
- Functional Scope：
  - CHANGE C 与首批范围：CHANGE C 成立。首批候选注册范围为 OKX 官方公开、应用能够通过公开接口拉取的永续合约；BTC 继续只作环境参照，不作为信号卡标的。
  - 候选与启用分层：可发现不等于可启用。公开永续目录可形成候选注册记录，但只有完成逐币数据源核验并通过启用门的标的，才可出现在选择器和卡片中。
  - 标的列表：首版只做名称/代码搜索、收藏、选中态、空结果和不可用状态；不承诺后台自动发现、自动评估或自动扫描整个市场。
  - 首页布局：固定提供 4/6/9 三档，首次访问默认 4 卡；档位就是布局切换，不另设独立“卡片数量”与“布局”控制。
  - 单卡切换：每张卡独立绑定一个已启用标的，切换不得串改其他卡；同一标的不能同时占用多个卡槽。
  - 配置持久化：布局档位、卡槽顺序/标的和收藏保存在服务端本地 SQLite；首版面向单用户、单实例本地运行，不含账号、跨设备同步或多人隔离。
  - 状态与证据：沿用十态状态机、六层评分、BTC 环境闸门、UTC 存储与 Asia/Shanghai 展示，以及 value/source/timestamp/freshness/status 证据要求。
  - 数据异常：单标的数据失败必须局部隔离，其他卡片继续展示；失败卡显示 stale/missing/unavailable 与真实原因，不用历史快照冒充实时行情。
  - 研究隔离：新增且无独立历史基线的标的只进入实时观察层；历史事件、相似性及 Precision/Recall/FPR/Success Rate/MFE/MAE 显示“未知/缺失”或不展示，且不混入既有研究分母。
  - 统一规则边界：新标的可复用现有阈值、六层权重、十态状态机和 Hard Veto 作为“统一观察规则/待验证”，不得表述为已由该标的样本外数据验证；禁止散落单币特判。
- Out of Scope：
  - 自动全市场扫描、自动选币、自动启用新合约、自动生成关注列表，或承诺覆盖 OKX 未来新增的每个永续合约。
  - OKX 公开永续范围之外的币种、其他交易所扩展，以及把 BTC 改为可选信号卡。
  - 自由增删任意卡数、重复卡、拖拽自由画布、多看板与分享模板。
  - 账号系统、云同步、跨设备恢复、多人配置隔离；Vercel 生产持久化方案在本 Plan 不拍板、不实施。
  - 自动交易、下单、仓位、止盈止损、收益承诺、开仓/平仓建议。
  - 在 ActionCard、实时信号或报警中展示胜率、准确率、假突破概率、Precision/Recall/FPR/Success Rate 等离线研究指标。
  - 为赶进度修改 `indicators.ts` 核心算法、既有冻结样本口径，或把其他标的样本冒充新增标的基线。
- Technical Approach：
  - 建立单一标的注册表，区分 `candidate`、`verified`、`enabled`、`disabled` 状态；展示、拉取、排序、OKX instrument ID、数据精度、启用状态和研究基线状态均从注册表派生，禁止散落币种数组。
  - 候选目录可由 OKX 官方公开永续列表生成或更新，但生成候选记录本身不得触发实时信号计算；启用必须经过逐币核验清单与显式状态变更，不做无人审核的自动全市场扫描。
  - 将 market overview 的分标信号、价格、K 线、资金费率、诊断和 freshness 改为以标的 ID 为键的映射；BTC 环境对象保持独立语义。
  - 将 LiveRadar 改为“档位 → 有序卡槽数组 → 按槽渲染”；每个卡槽拥有稳定 slotId 与 assetId，单卡切换只更新对应卡槽。服务端按唯一标的去重行情请求。
  - 选择器禁用已占用标的；扩档时按确定性补位规则填充，已启用标的不足则保留空槽，不制造重复卡。
  - 配置通过集中 Repository/Service 和服务端 API 读写 SQLite，浏览器不得直接接触 `.db` 或散落 SQL。配置表至少保存 schema version、布局档位、有序卡槽、收藏与更新时间。
  - SQLite 遵守 `docs/sop/sqlite.md`：稳定 `project_slug=pepe-doge-breakout-radar`；一个项目一个主库；开发库与生产库隔离；Migration 与 schema 进入 Git，真实 `.db`、备份及隐私数据不进入 Git；运行时路径由 `SQLITE_DB_PATH` 等环境变量注入，不在业务代码写死宿主机绝对路径。
  - 本地正式部署的宿主机主库归属 `DockerData/pepe-doge-breakout-radar/db/pepe-doge-breakout-radar.db`，备份归属 `DockerBackups/pepe-doge-breakout-radar/sqlite/`；容器内建议路径为 `/app/data/db/pepe-doge-breakout-radar.db`，以 bind mount 持久化。
  - SQLite 初始化/连接评估并记录 `foreign_keys=ON`、WAL 与 `busy_timeout`；正式 Migration 前备份，恢复先在隔离环境执行 `integrity_check`、`foreign_key_check`、schema version、关键行数与业务读取验证。
  - Vercel 文件系统不能作为本方案的持久化承诺；在生产持久化架构另行决策前，Vercel 不作为配置持久化验收环境，不得把临时文件写入描述为可靠保存。
  - 测试覆盖：注册表状态门、4/6/9 切换、默认 4 卡、单卡隔离、一币一卡、确定性补位、收藏/搜索、SQLite Migration 与损坏恢复、服务重启持久化、单标失败隔离、无基线文案、实时层无研究指标，以及既有 73 项单测与 21 事件回归不退化。
- Data / API：
  - 现状事实：当前 `ASSETS`、`TRADE_COINS`、`AssetId`、overview payload 与 LiveRadar 固定为 PEPE/DOGE/ETHFI；BTC 独立承担环境参照，ETHFI 无历史研究基线。
  - OKX 候选范围定义：以核验时 OKX 官方公开接口返回、且类型为永续合约的 instrument 为候选；“全量币池”只表示候选注册范围，不表示所有候选已验证、已启用或正在被自动扫描。
  - 每个标的启用前必须逐币记录并通过：官方 instrument ID 与永续类型、交易/上线状态、4H K 线可拉取性与必要历史长度、成交量字段/口径、资金费率可用性、价格与数量精度、时间戳/收盘语义、限频响应，以及应用端真实请求结果。任一必需项失败或证据过期，不得设为 `enabled`。
  - 首批启用集合不是预写死的币名清单，而是首轮核验时从上述 OKX 候选范围中逐币通过启用门的集合；核验结果需形成可审计清单。PEPE、DOGE、ETHFI 也须纳入同一注册表与启用状态治理。
  - `GET /api/market/overview` 目标形态支持动态标的映射与分标诊断；开发时需提供现有三币消费者的迁移方案。
  - `GET /api/market/candles`、`GET /api/market/funding` 只接受已注册且 `enabled` 的标的；未知、未核验、停用标的返回可解释错误。第三方失败继续返回真实诊断，不用快照冒充实时。
  - 新增服务端配置 API 仅服务单用户布局/收藏；需校验 4/6/9、卡槽唯一性、标的启用状态及 schema version，并采用原子事务写入。
  - SQLite 的表结构与 Migration 编号在开发前由实现计划冻结；真实数据库文件、备份和生产配置数据不进入仓库。
- Key Assumptions：
  - 用户需要固定档位的观察盘，而不是无限画布；该假设已由“4/6/9 且档位即布局”决策确认。
  - 一币一卡、搜索加收藏是首版足够的组织方式；已由人类决策确认。
  - 首次访问默认 4 卡是满足已批准最小档位的产品默认值；用户可立即切换为 6 或 9，若启用标的不足则显示空槽。
  - 单用户、低写入、单实例本地运行适合 SQLite；若进入多用户、多实例、跨设备同步或高并发写入，则重新评估 PostgreSQL/Supabase，不在 SQLite 上叠加复杂权限。
  - OKX 公开永续目录会变化，因此候选范围是运行时目录事实而非计划中永久固定的币名列表；启用证据必须带核验时间，过期/下架时可停用且配置安全降级。
  - 新标的复用统一阈值、权重和状态机，只表示采用同一观察框架，不代表这些规则已在该标的上验证。
  - BTC 继续仅作为环境参照，不占卡槽、不进入可选币池；已由本轮范围决策冻结。
- Competitor / Research Summary：
  - 已核实现状：当前首页固定三卡，现有代码与 API 存在三币固定结构；PEPE/DOGE 有历史样本，ETHFI 无独立研究基线。
  - 人类决策已冻结交互抽象：名称/代码搜索、收藏、一币一卡及 4/6/9 布局；本产品不复制交易所的下单、订单簿或收益导向模块。
  - 外部逐币事实不在计划阶段先验宣称；以 OKX 官方公开数据和应用端真实请求为启用证据。未完成核验的候选只留在注册层，不进入用户可见实时卡。
- Risks：
  - 目录漂移：OKX 新增、下架或暂停合约会使候选池变化；需记录核验时间、定期复核并在停用时安全移除卡槽绑定。
  - 研究误导：统一规则在新标的上未经样本外验证；必须持续标注“统一观察规则/待验证”，研究层保持未知/缺失。
  - 数据异质性：不同合约的历史长度、流动性、成交量口径、资金费率、精度与限频不同；逐币启用门是强制前置条件。
  - 性能/限频：全量候选目录不能等价为全量实时拉取；实时请求仅覆盖当前布局中的唯一已启用标的，并按 instrument 去重、限频与缓存。
  - 配置一致性：标的停用、Migration 失败或数据库损坏可能使布局非法；需事务、版本迁移、回退、备份与隔离恢复演练。
  - 部署差异：本地 SQLite 可通过持久卷保存，Vercel 文件系统短暂；未另定生产数据库前，不能承诺 Vercel 跨部署持久化。
  - 单用户边界：若公网多人共享同一 Vercel 实例，服务端单份配置会互相覆盖；因此账号/多租户与生产持久化必须作为后续独立决策。
